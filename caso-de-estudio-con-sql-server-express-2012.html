    3. Caso de estudio con SQL Server Express 2012

    3.1. Introduction

    La mayoría de los ejemplos que se encuentran en Internet sobre Entity Framework son ejemplos con SQL Server. Esto es bastante normal. Es probable que sea el SGBD más utilizado en el mundo .NET de las empresas. Vamos a seguir esta tendencia. Posteriormente, los ejemplos se ampliarán a todas las bases de datos mencionadas en el párrafo 1.2.

using System.Data.Entity;
using RdvMedecins.Entites;

namespace RdvMedecins.Models
{

  // el contexto
  public class RdvMedecinsContext : DbContext
  {
    // los médicos
    public DbSet<Medecin> Medecins { get; set; }

  public class RdvMedecinsInitializer : DropCreateDatabaseAlways<RdvMedecinsContext>

    • línea 8: la clase [RdvMedecinsContext] representará el contexto de persistencia, c.-à-d. el conjunto de entidades administradas por ORM. Debe derivarse de la clase [System.Data.Entity.DbContext];
    • línea 11: el campo [Medecins] representará las entidades de tipo [Medecin] del contexto de persistencia. Es de tipo DbSet<Médico>. Por lo general, habrá tantos [DbSet] como tablas en la base de datos, uno por tabla;
    • línea 15: se define una clase [RdvMedecinsInitializer] para inicializar la base de datos creada. Aquí deriva de la clase [DropCreateDataBaseAlways], que, como su nombre lo indica, elimina la base de datos si ya existe y luego la vuelve a crear. Esto resulta práctico durante la fase de desarrollo de la clase BD. El parámetro de la clase [DropCreateDataBaseAlways] es el tipo de contexto de persistencia asociado a la base de datos. Se pueden utilizar otras clases padre distintas de [DropCreateDataBaseAlways] para la clase de inicialización:
    • [DropCreateDatabaseIfModelChanges]: recrea la base de datos si las entidades han cambiado,
    • [CreateDatabaseIfNotExists]: crea la base de datos si no existe;

    Vamos a reducir la dependencia de las convenciones de EF mediante el uso de anotaciones. El código de la entidad en [Entites.cs] queda así:

    
using System;
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

namespace RdvMedecins.Entites
{
  [Table("MEDECINS", Schema = "dbo")]
  public class Medecin
  {
    // datos
    [Key]
    [Column("ID")]
    public int Id { get; set; }
    [Required]
    [MaxLength(5)]
    [Column("TITRE")]
    public string Titre { get; set; }
    [Required]
    [MaxLength(30)]
    [Column("NOM")]
    public string Nom { get; set; }
    [Required]
    [MaxLength(30)]
    [Column("PRENOM")]
    public string Prenom { get; set; }
    [Required]
    [Column("VERSION")]
    public int Version { get; set; }
  }
}
    • líneas 2 y 3: las anotaciones se encuentran en los espacios de nombres [System.ComponentModel.DataAnnotations] (Key, Required, MaxLength) y [System.ComponentModel.DataAnnotations.Schema] (Column). Se pueden encontrar otras anotaciones en URL y [http://msdn.microsoft.com/en-us/data/gg193958.aspx];
    • línea 11: [Key] designa la clave primaria;
    • línea 12: [Column] establece el nombre de la columna correspondiente al campo;
    • línea 14: [Required] indica que el campo es obligatorio (SQL, NOT, NULL);
    • línea 15: [MaxLength] establece el tamaño máximo de la cadena de caracteres, [MinLength] su tamaño mínimo;

    Ejecutemos el proyecto con esta nueva definición de la entidad [Medecin]. La base de datos creada es entonces la siguiente:

     
    • las columnas tienen el nombre que les hemos asignado;
    • la anotación [Required] se ha traducido como SQL, NOT y NULL;
    • la anotación [MaxLength(N)] se tradujo a un tipo SQL nvarchar(N).

    En la aplicación NHibernate, la columna [VERSION] servía para evitar accesos concurrentes a una misma fila de una tabla. El principio es el siguiente:

    • un proceso P1 lee una fila L de la tabla [MEDECINS] en el momento T1. La fila tiene la versión V1;
    • un proceso P2 lee la misma fila L de la tabla [MEDECINS] en el momento T2. La fila tiene la versión V1 porque el proceso P1 aún no ha validado su modificación;
    • el proceso P1 valida su modificación de la línea L. La versión de la línea L pasa entonces a V2 = V1 + 1;
    • el proceso P2 valida su modificación de la línea L. El proceso ORM lanza entonces una excepción porque el proceso P2 tiene una versión V1 de la línea L diferente de la versión V2 encontrada en la base de datos.

    A esto se le llama gestión optimista de accesos concurrentes. Con EF 5, un campo que desempeña esta función debe tener uno de los dos atributos: [Timestamp] o [ConcurrencyCheck]. SQL Server tiene un tipo [timestamp]. En una columna con este tipo, SQL Server genera automáticamente su valor cada vez que se inserta o modifica una fila. Dicha columna puede utilizarse entonces para gestionar la concurrencia de acceso. Retomando el ejemplo anterior, el proceso P2 encontrará un timestamp diferente al que leyó, ya que, mientras tanto, la modificación realizada por el proceso P1 lo habrá alterado.

    3.4.2. La entidad [Creneau]

    La tabla [CRENEAUX] enumera los intervalos de tiempo en los que son posibles los RV:

    • ID: número que identifica el intervalo de tiempo —clave primaria de la tabla
    • VERSION: número que identifica la versión de la fila en la tabla. Este número se incrementa en 1 cada vez que se realiza una modificación en la fila.
    • ID_MEDECIN: número que identifica al médico al que pertenece este horario – clave externa en la columna MEDECINS (ID).
    • HDEBUT: hora de inicio de la franja horaria
    • MDEBUT: minutos de inicio del horario
    • HFIN: hora de finalización del horario
    • MFIN: minutos de fin de la franja

    La segunda línea de la tabla [CRENEAUX] (véase [1] más arriba) indica, por ejemplo, que el horario n.º 2 comienza a las 8:20 y termina a las 8:40, y pertenece a la doctora n.º 1 (la Sra. Marie PELISSIER).

    Con lo que sabemos, podemos definir la entidad [Creneau] de la siguiente manera en [Entites.cs]:

    [Required]
    [Column("MDEBUT")]
    public int Mdebut { get; set; }
    [Required]
    [Column("HFIN")]
    public int Hfin { get; set; }

    Tenemos una base de datos llena. La vamos a vaciar. Creamos una nueva clase [Erase.cs] en el proyecto actual [1]:

    Volvamos a la arquitectura en capas de una aplicación como la del caso de estudio:

    • las entidades [Creneau] vinculadas a las citas;
    • las entidades [Medecin] vinculadas a esos horarios;
    • las entidades [Clients] vinculadas a las citas.

    • un proceso P1 lee una fila L de la tabla [MEDECINS] en el momento T1. La fila tiene el timestamp TS1;

    • el proceso P1 valida su modificación de la línea L. El timestamp de la línea L pasa entonces a TS2;
    • el proceso P2 valida su modificación de la línea L. ElORM genera entonces una excepción porque el proceso P2 tiene un timestamp TS1 de la línea L diferente del timestamp TS2 encontrado en la base de datos.

Dicha columna puede utilizarse entonces para gestionar la concurrencia de acceso.

    3.7. Conclusion

    Hemos completado con éxito la adaptación de una aplicación ASP.NET / NHibernate:

    a una aplicación ASP.NET / EF 5:

    Aunque esta arquitectura debería habernos permitido mantener intacta la capa [ASP.NET], tuvimos que modificarla por dos razones:

    • las entidades no eran exactamente iguales. El tipo de las claves primarias de las entidades NHibernate era int, mientras que el de EF 5 era int?. Esto nos llevó a introducir cast en el código web;
    • el modo de carga de las entidades no era el mismo para las dos: carga anticipada (Eager Loading) para NHibernate y carga diferida (Lazy Loading) para EF 5. Esto nos llevó a ampliar la interfaz de la capa [DAO] con un método genérico que permite buscar una entidad mediante su clave primaria.

    Sin embargo, la migración resultó bastante sencilla, lo que justifica una vez más, si es que hacía falta, la arquitectura en capas y la inyección de dependencias con Spring u otro marco de inyección de dependencias.
