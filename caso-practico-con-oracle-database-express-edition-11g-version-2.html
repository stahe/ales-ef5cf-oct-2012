    5. Caso práctico con Oracle Database Express Edition 11g Versión 2

    5.1. Instalación de las herramientas

    Las herramientas que se deben instalar son las siguientes:

    • el SGBD: [http://www.oracle.com/technetwork/products/express-edition/downloads/index.html];
    • una herramienta de administración: EMS SQL Manager for Oracle Freeware [http://www.sqlmanager.net/fr/products/oracle/manager/download];
    • un cliente de Oracle para .NET: ODAC 11.2 Release 5 (11.2.0.3.20) con Oracle Developer Tools para Visual Studio: [http://www.oracle.com/technetwork/developer-tools/visual-studio/downloads/index.html].

    En los siguientes ejemplos, el usuario «system» tiene la contraseña «system».

    Iniciemos Oracle [1] y luego la herramienta [SQL Manager Lite for Oracle], con la cual administraremos SGBD y [2].

    • En [3], nos conectamos a una base de datos existente;
    • en [4], utilizamos el servicio de Oracle XE para conectarnos;
    • en [5], indicamos el nombre de la base de datos XE;
    • en [6], nos conectamos como system / system;
    • en [7], finalizamos el asistente;
    • en [8], se inicia sesión en la base de datos;
    • en [9], ya estamos conectados;
    • como nos hemos conectado como el usuario system / system, que cuenta con derechos ampliados, podremos, por ejemplo, administrar los usuarios [10];
    • en [11], creamos un nuevo usuario;
    • en [12], se llamará [RDVMEDECINS-EF];
    • en [13], y tendrá la contraseña rdvmedecins;
    • en [14], se confirma la creación del usuario;
    • en [15], el usuario ha sido creado;
    • en [16], el usuario [RDVMEDECINS-EF] también es un esquema de base de datos;
    • en [17], el usuario, tal como se creó, no tiene suficientes derechos. Le otorgamos derechos mediante un script SQL;
    • en [18], el script ejecutado;
    • en [19], intentaremos iniciar sesión con la identidad de [RDVMEDECINS-EF] para ver qué puede hacer. Para ello, comenzamos por registrar una nueva base de datos en [EMS Manager];
    • en [19], nos conectamos a través del servicio XE;
    • en [20], nos conectamos con la identidad RDVMEDECINS-EF / rdvmedecins;
    • en [21], se asigna un alias que refleja el nombre del usuario que ha iniciado sesión;
    • en [22], se inicia sesión en Oracle con la información proporcionada;
    • En [22], logramos conectarnos;
    • en [23], intentamos crear una tabla en el esquema [RDVMEDECINS-EF];
    • en [24], se define una tabla cualquiera;
    • en [25], se valida su definición;
    • en [26], la tabla se ha creado. La eliminamos;
    • en [27], ya se ha eliminado.

    Ahora que contamos con un usuario con los derechos suficientes, crearemos el proyecto VS 2012, el cual generará las tablas del esquema [RDVMEDECINS-EF] a partir de la definición de las entidades.

    Recordamos haber tenido el mismo error con MySQL. Esto se debe al tipo del campo Timestamp de las entidades. Realizamos la misma modificación. En las entidades, reemplazamos las tres líneas

    
    [Column("TIMESTAMP")]
    [Timestamp]

    por las siguientes:

    
    [ConcurrencyCheck]
    [Column("VERSIONING")]
    public int? Versioning { get; set; }

    Por lo tanto, cambiamos el tipo de la columna de byte[] a int?. Recordemos que tanto para SQL Server como para MySQL, la columna de las tablas que se utilizaba para gestionar la concurrencia de acceso recibía un valor de SGBD cada vez que se insertaba o modificaba una fila. A partir de ahora, utilizaremos un campo de entidad que será un entero. En el SGBD, utilizaremos procedimientos almacenados para incrementar este entero en una unidad cada vez que se inserte o modifique una fila.

  public class RdvMedecinsInitializer : DropCreateDatabaseAlways<RdvMedecinsContext>

    La base de datos solo se crea si no existe. Volvemos a ejecutar [CreateDB_01.cs] y ya no hay errores. Sin embargo, en [EMS Manager], observamos que la base de datos [RDVMEDECINS-EF] se ha quedado vacía. Como EF 5 encontró una base de datos existente, no hizo nada. Solo realiza alguna acción si la base de datos no existe. A partir de ahí, nos encontramos en un círculo vicioso. De hecho, la cadena de conexión para SGBD es la siguiente:

    
  <connectionStrings>
    <add name="monContexte" connectionString="Data Source=(DESCRIPTION=(ADDRESS_LIST=(ADDRESS=(PROTOCOL=TCP)(HOST=localhost)(PORT=1521)))(CONNECT_DATA=(SERVER=DEDICATED)(SERVICE_NAME=XE)));User Id=RDVMEDECINS-EF;Password=rdvmedecins;" providerName="Oracle.DataAccess.Client" />
</connectionStrings>

    En la línea 2, la cadena de conexión no utiliza el nombre de una base de datos, sino el nombre de un usuario. Este debe existir.

    Por lo tanto, nos vemos obligados a crear la base de datos [RDVMEDECINS-EF] manualmente con la herramienta [EMS Manager for Oracle]. No describiremos todos los pasos, sino solo los más importantes.

    La base de datos de Oracle será la siguiente:

    Las tablas

    Las distintas tablas tienen las claves primarias y externas que tenían esas mismas tablas en los dos ejemplos anteriores. Las claves externas tienen, en particular, el atributo ON, DELETE y CASCADE.

    Las secuencias

    Aquí se han creado secuencias de Oracle. Son generadores de números consecutivos. Hay 5: [1].

    • En [2], vemos las propiedades de la secuencia [SEQUENCE_CLIENTS]. Genera números consecutivos de 1 en 1, desde 1 hasta un valor muy grande.

    Todas las secuencias siguen el mismo modelo.

    • [SEQUENCE_CLIENTS] se utilizará para generar la clave primaria de la tabla [CLIENTS];
    • [SEQUENCE_MEDECINS] se utilizará para generar la clave primaria de la tabla [MEDECINS];
    • [SEQUENCE_CRENEAUX] se utilizará para generar la clave primaria de la tabla [CRENEAUX];
    • [SEQUENCE_RVS] se utilizará para generar la clave primaria de la tabla [RVS];
    • [SEQUENCE_VERSIONS] se utilizará para generar los valores de las columnas [VERSIONING] de todas las tablas.

    Los disparadores

using (var context = new RdvMedecinsContext())
      {
        // aquí tenemos un nuevo contexto vacío
        // se agrega «cliente1» al contexto para eliminarlo
        context.Clients.Remove(context.Clients.Find(client1.Id));
        // se guarda el contexto
        context.SaveChanges();
      }

    5.3. Arquitectura multicapa basada en EF 5

    Volvemos a nuestro caso de estudio descrito en el párrafo 2, página 7.

    Comenzaremos por construir la capa de acceso a datos [DAO]. Para ello, duplicamos el proyecto de consola VS 2012 [RdvMedecins-SqlServer-02] en [RdvMedecins-Oracle-02] [1]:

    • en [2], eliminamos el proyecto [RdvMedecins-SqlServer-02];
    • en [3], se agrega un proyecto existente a la solución. Se toma de la carpeta [RdvMedecins-Oracle-02] que se acaba de crear;
    • en [4], el nuevo proyecto lleva el nombre del que se eliminó. Vamos a cambiarle el nombre;
    • en [5], hemos cambiado el nombre del proyecto;
    • en [6], modificamos algunas de sus propiedades, como en este caso el nombre del ensamblado;
    • en [7], se elimina la carpeta [Models] para sustituirla por la carpeta [Models] del proyecto [RdvMedecins-Oracle-01]. De hecho, ambos proyectos comparten las mismas plantillas.
    • en [8], las referencias actuales del proyecto;
    • en [9], se ha agregado el conector ADO.NET de Oracle con la herramienta NuGet.

    En el archivo [App.config], se reemplaza la información de la base de datos SQL Server por la de la base de datos Oracle. Esta información se encuentra en el archivo [App.config] del proyecto [RdvMedecins-Oracle-01]:
